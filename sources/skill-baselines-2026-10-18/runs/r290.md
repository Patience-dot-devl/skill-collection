## Blog post

# Ferrous Postgres CDC Is Now Generally Available

Today we are announcing that the Ferrous Postgres change-data-capture (CDC) connector is generally available. Teams can now stream row-level changes from their PostgreSQL databases to the systems that depend on them, with sub-second latency and without the operational risks that have made logical replication difficult to run in production.

## Why change data capture matters

Many applications need to react when data changes. Search indexes, analytics warehouses, caches, notification services and downstream microservices all depend on an up-to-date copy of operational data. The older approach, polling tables for new rows, is slow, and it puts repeated query load on the primary database. Change data capture reads the database's own change log instead, so every insert, update and delete is captured as it happens. Common uses include keeping a search index in sync with a product catalogue, feeding change events into a data warehouse, and invalidating caches the moment source data changes.

PostgreSQL supports this through logical replication and replication slots. Slots are powerful, but they have a well-known failure mode. If a consumer falls behind or stops, the slot holds back write-ahead log (WAL), and the disk on the primary can fill up. Many teams have learned this lesson during an incident.

## What generally available means

General availability means the connector is ready for production workloads. It is no longer labelled as a preview. We treat its configuration and behaviour as stable, and changes are described in the release notes so that upgrades are predictable.

## Latency you can measure

In our benchmark, the connector delivers sub-second end-to-end latency. At a sustained rate of 20,000 rows per second, the p95 end-to-end latency was 420 ms. We publish these numbers so you can compare them with your own requirements. The full benchmark setup is described in [benchmark report link], and we encourage you to run the same kind of test on your own hardware and workload.

## No slot bloat from heartbeats

The connector addresses the slot problem with slot heartbeats. It keeps advancing its replication slot even when the tables it follows are quiet. As a result, the slot does not hold on to WAL that the connector has already processed. Disk usage on the primary stays predictable, and your team does not need to watch the slot by hand.

## Open source under Apache-2.0

The connector is open source under the Apache License 2.0. You can read the source, run it in your own infrastructure, audit how it handles your data, and contribute fixes or features. Data movement is too important to be a black box. Apache-2.0 also allows you to use the connector in commercial products.

## Or run it on Ferrous Cloud

If you would rather not operate the connector yourself, Ferrous Cloud offers a managed version. The managed service takes care of deployment and day-to-day operations, so the work of running the connector sits with us. It builds on the same open-source connector, so the behaviour you test locally is the behaviour you get in the cloud.
